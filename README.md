# RMS TableCard / RMS-COUVERT

Сервис управления электронными табличками: веб-интерфейс, генерация JPEG с ФИО и должностью и отправка изображения через TableCard Gateway. Сервер и интерфейс обслуживаются одним приложением FastAPI.

Приложение можно запускать на компьютере оператора или на самом шлюзе NC-LCDSRV-NG. Порт **8000** используется для нашего интерфейса, порт **5003** — для API шлюза, управляющего табличками.

## Структура

```text
RMS-tablecard/
├── app/
│   ├── main.py                   # Сервер и API
│   ├── config.json               # Адрес и порт шлюза
│   ├── devices.json              # Список табличек и их локальные статусы
│   ├── requirements.txt          # Зависимости с дополнительными компонентами Uvicorn
│   ├── requirements.runtime.txt  # Зависимости без дополнительных компонентов Uvicorn
│   └── static/                   # HTML, JavaScript, стили и изображения
├── deploy/
│   └── systemd/
│       └── rms-tablecard.service # Автозапуск на Linux, порт 8000
├── docs/
│   ├── linux-gateway.md          # Установка на шлюз Debian/Ubuntu
│   └── legacy-notes.md           # Сохранённая заметка из прежней структуры
├── tests/
│   ├── test_devices.py           # Поиск, статусы и сохранение устройств
│   └── test_render.py            # Совпадение предпросмотра с отправленным JPEG
├── .gitignore
└── README.md
```

Единственная рабочая версия сервиса находится в `app/`. Конфигурация, список устройств и статические файлы загружаются относительно `app/main.py`. Каталог `venv/` создаётся локально и не хранится в Git.

`docs/legacy-notes.md` и `app/static/search.jpg` — сохранённые старые материалы; действующий интерфейс их не использует.

## Запуск в Windows

Все команды выполняются в PowerShell из корня репозитория.

Если окружение `venv` уже создано и зависимости установлены:

```powershell
.\venv\Scripts\python.exe -m uvicorn main:app --app-dir .\app --host 127.0.0.1 --port 8000 --workers 1
```

Для новой установки сначала создайте окружение и установите зависимости:

```powershell
py -m venv venv
.\venv\Scripts\python.exe -m pip install -r .\app\requirements.txt
```

После этого выполните команду запуска выше. Активация окружения не требуется, поскольку используется его интерпретатор напрямую. Остановка сервиса — `Ctrl+C`.

Откройте <http://127.0.0.1:8000/>. Для работы с физическими табличками сначала укажите адрес API шлюза в `app/config.json`, как описано ниже.

## Запуск в Linux

Для Debian/Ubuntu нужны Python с модулем `venv`, команда `ping` и шрифты DejaVu. Их установка описана в [инструкции для шлюза](docs/linux-gateway.md). Команды запуска из корня репозитория:

```bash
python3 -m venv venv
./venv/bin/python -m pip install -r app/requirements.runtime.txt
./venv/bin/python -m uvicorn main:app --app-dir app --host 0.0.0.0 --port 8000 --workers 1
```

Эта команда открывает сервис для локальной сети по `http://IP-шлюза:8000/`, если запущена на самом шлюзе и порт 8000 свободен и доступен по сети. Штатный веб-интерфейс шлюза остаётся на своём порту.

Если на порту 8000 уже работает старая версия нашего приложения, остановите её перед запуском новой. Не запускайте два экземпляра сервиса с одним `devices.json`.

Для установки на NC-LCDSRV-NG с Debian/Ubuntu и запуска после перезагрузки используйте [инструкцию автозапуска](docs/linux-gateway.md) и готовый [unit-файл systemd](deploy/systemd/rms-tablecard.service).

Для отображения кириллицы при генерации изображений нужны шрифты DejaVu Sans в `/usr/share/fonts/truetype/dejavu/`. В Windows сервис использует Arial из `C:/Windows/Fonts/`. Собственный файл шрифта можно указать через переменную окружения `TC_FONT_PATH`.

## Доступ к интерфейсу и API

- Интерфейс: <http://127.0.0.1:8000/>
- Swagger: <http://127.0.0.1:8000/docs>
- Проверка работы сервиса: <http://127.0.0.1:8000/health>

Для доступа с других компьютеров в локальной сети используется `--host 0.0.0.0`: он уже указан в Linux-команде и службе systemd. В команде для Windows при необходимости замените `--host 127.0.0.1` на `--host 0.0.0.0`. Открывайте `http://<IP компьютера или шлюза>:8000/`; интерфейс и API используют один и тот же порт.

Интерфейс автоматически отправляет API-запросы на тот адрес, с которого открыт. В верхнем меню находится кнопка **Таблички**; ссылок на Swagger, Health и JSON в меню нет. Диагностические маршруты доступны напрямую. Получение исходного списка устройств шлюза через `/devices/sync` требует POST-запроса, например:

```powershell
Invoke-RestMethod -Method Post -Uri 'http://127.0.0.1:8000/devices/sync'
```

## Подключение к шлюзу

В `app/config.json` задаются `gateway_host` и `gateway_port`. Адрес `127.0.0.1:5003` подходит, когда TableCard Gateway работает на той же машине. При запуске с компьютера оператора укажите IP шлюза, например `10.30.30.253`, и порт его API `5003` (порт `8000` обслуживает наш интерфейс). После ручного изменения файла перезапустите сервис. Изменения через API `/config` или `/gateway/set` применяются сразу.

| Где запущено приложение | Адрес интерфейса в браузере | `gateway_host` | `gateway_port` |
|---|---|---|---|
| На компьютере оператора | `http://127.0.0.1:8000/` на этом компьютере | IP шлюза, например `10.30.30.253` | `5003` |
| На самом шлюзе | `http://IP-шлюза:8000/` с компьютера в его сети | `127.0.0.1`, если API шлюза слушает локально | `5003` |

Пример `app/config.json` для запуска приложения на самом шлюзе:

```json
{
  "gateway_host": "127.0.0.1",
  "gateway_port": 5003
}
```

Если приложение запущено на компьютере оператора, измените `gateway_host` на фактический IP шлюза. `0.0.0.0` — адрес прослушивания сервера; в браузере и в `gateway_host` используйте адрес нужной машины.

Переменные `TC_GATEWAY_HOST` и `TC_GATEWAY_PORT` задают исходные значения; параметры из `app/config.json` имеют приоритет. `/health` проверяет сам сервис, а не доступность шлюза.

Для просмотра интерфейса и генерации JPEG шлюз не нужен. Для получения списка табличек и отправки изображений шлюз должен быть доступен.

## Работа оператора

1. Включите шлюз и таблички. Дождитесь автопоиска или нажмите **Найти новые таблички** справа от списка выбора. Под кнопкой указан интервал автопоиска.
2. Откройте **Таблички** в верхнем меню. Сверьте MAC-адреса, задайте названия безымянным устройствам и нажмите **Сохранить названия**.
3. Выберите табличку в выпадающем списке. Её MAC и профиль подставляются автоматически; ручного ввода MAC нет.
4. Введите ФИО и должность. Выберите шрифты, цвета, размеры, положение текста и при необходимости изображение фона. Кнопки **B**, **I**, **U** меняют начертание ФИО.
5. Проверьте предпросмотр и нажмите **⤴** рядом с выбором изображения. Отправка доступна только при выбранной табличке и готовом актуальном превью.
6. После успешного ответа на отправку интерфейс помечает табличку `filled` и скрывает её из выбора. Затем отдельно ожидает подтверждение от устройства. Если подтверждение не получено, проверьте экран таблички.

Кнопка **⟳** рядом со списком намеренно сбрасывает **все** сохранённые статусы на `base`, разрешая повторную отправку. Обычный поиск новых табличек этого не делает.

## Предпросмотр

Превью получает готовый JPEG через `POST /render`, используя тот же серверный рендерер, что и отправка на табличку. Шрифты, переносы строк, отступы, обрезка фона и JPEG-сжатие совпадают. Размер и пропорции превью соответствуют профилю выбранной таблички: `nameplate7` — 1024 × 600, `nameplate10` — 1600 × 720. До выбора устройства используется `nameplate7`. Отправка доступна после выбора таблички из списка; её MAC и профиль берутся из сохранённой записи.

Изменение текста, оформления, фона или профиля обновляет превью с небольшой задержкой. Пока актуальное изображение не готово или его загрузка завершилась ошибкой, отправка недоступна. Старые ответы сервера не подменяют новый предпросмотр. Интерфейс отправляет настройки показанного изображения и его SHA-256; перед обращением к шлюзу сервер проверяет совпадение JPEG. Если изображение изменилось, отправка отклоняется с HTTP 409. Для прежних API-клиентов поле `expected_jpg_sha256` в `POST /push` остаётся необязательным.

Превью отражает отправляемое изображение. Яркость и цветопередача физического дисплея, а также значки батареи и другие элементы, которые рисует прошивка таблички, в JPEG не входят.

Шрифт выбирается отдельно в блоках **ФИО** и **Должность**. Список из `GET /fonts` содержит доступные на сервере поддерживаемые семейства: Arial, Times New Roman, Georgia, Verdana, Courier New и Trebuchet MS в Windows; DejaVu и Liberation в Linux, если установлены соответствующие файлы. Шрифт браузера оператора на рендер не влияет. По умолчанию используются Arial в Windows, DejaVu Sans в Linux или файл `TC_FONT_PATH`, если он задан. Жирное и курсивное начертания используют соответствующие файлы семейства; для одиночного `TC_FONT_PATH` используется один указанный файл. Неизвестный или недоступный выбранный шрифт вызывает ошибку, а не молча заменяется другим. В API выбор передаётся в `text.fio.font_family` и `text.title.font_family`.

## Список табличек

В `app/devices.json` у каждой таблички указываются:

- `mac` — MAC-адрес;
- `name` — отображаемое название;
- `profile` — `nameplate7` (1024 × 600) или `nameplate10` (1600 × 720);
- `status` — локальный статус `base` или `filled`.

Сервис ищет новые таблички сразу после запуска и повторяет поиск через 15 секунд после завершения предыдущего запроса, даже если браузер закрыт. Каждый новый корректный MAC со статусом шлюза `online` добавляется один раз с `name: ""`, `profile: "nameplate7"` и `status: "base"`. Записи шлюза со статусом `offline` или без подтверждённого `online` не добавляются. Имена, профили и статусы существующих табличек сохраняются. Отключённые устройства остаются в файле. Ошибка шлюза не меняет файл; повреждённый JSON не заменяется пустым списком.

Размер экрана автоматически не определяется: **все новые таблички получают `nameplate7`**. Для 10-дюймового устройства администратор должен заранее установить `profile: "nameplate10"` в его записи. Операторское окно меняет только названия. Профиль можно изменить через API `/devices/file` или вручную в `app/devices.json` при остановленном сервисе, затем запустить его снова.

Для новой установки без заранее зарегистрированных табличек начальное содержимое `app/devices.json`:

```json
{
  "devices": []
}
```

При обновлении работающей установки сохраняйте её существующий файл с названиями и статусами. Если файл отсутствует, сервис начинает с пустого списка и создаёт его при обнаружении новой таблички.

В интерфейс попадают устройства с локальным статусом `base` и статусом шлюза `online`, которые отвечают на ping с машины, где запущен сервис. Шлюз может хранить старую запись `offline` с тем же IP, который уже получила другая табличка: такая запись не показывается, даже если этот IP отвечает на ping. MAC берётся из ответа шлюза; записи с разными MAC не объединяются по IP. Для таблички без имени отображается её MAC. Список в активной вкладке обновляется каждые 15 секунд; во время отправки и при скрытой вкладке фоновое обновление интерфейса пропускается. Поля оператора сохраняются, а выбор удерживается, пока табличка остаётся доступной в списке. Поиск и обновление интерфейса независимы: появление новой таблички на странице может занять ещё один интервал обновления после добавления в файл.

- **Найти новые таблички** — немедленный поиск через `POST /devices/discover`, без изменения статусов существующих устройств.
- **⟳** — намеренно сбрасывает статусы всех записанных табличек на `base`, чтобы снова выдать им информацию.
- После успешного ответа `/push` интерфейс вызывает `/devices/mark_filled`: табличка скрывается ещё до подтверждения обновления экрана. Автопоиск не возвращает её в список. `filled` — защита от повторного назначения, а не подтверждение содержимого экрана. При прямом вызове API `/push` статус в файле автоматически не меняется.

Кнопка поиска находится справа от выбора таблички и MAC, подпись об автопоиске — под кнопкой. Ручного ввода MAC и нижнего поля технического статуса в интерфейсе нет. Поиск без новых устройств не показывает уведомление; ошибки и итог отправки отображаются краткими уведомлениями.

В верхнем меню **Таблички** оператор видит MAC-адреса и задаёт названия; безымянные таблички показаны первыми. Можно исправить и ранее заданное название. Сохранение меняет только имена: профили, статусы и одновременно обнаруженные устройства сохраняются. Окно доступно даже без связи со шлюзом. При одновременном изменении одного имени сервер возвращает конфликт, а правки остаются в полях. «Обновить список» загружает текущие имена и сохраняет несохранённый ввод для проверки и повторного сохранения. Кнопка Config и редактор JSON убраны из интерфейса оператора.

`GET /devices/names` возвращает только MAC и название каждой сохранённой таблички. `POST /devices/names` принимает `changes: [{mac, name, base_name}]`, где `base_name` — имя при загрузке списка. Название ограничено 120 символами. Эти операции не обращаются к шлюзу.

Под списком выбора показана причина отсутствия табличек: нет связи со шлюзом, устройства ещё не обнаружены, уже заполнены или недоступны. При ошибке сети проверьте Ethernet, питание шлюза и адрес в `app/config.json`. После восстановления связи список обновится автоматически; статусы `filled` при этом не сбрасываются.

Для программного редактирования остальных полей сохранён `POST /devices/file`: он принимает `devices` (отредактированный список) и `base_devices` (исходный список из `GET /devices/file`). Оба поля обязательны. Успешный ответ содержит итоговый массив `devices`, который следует использовать как основу следующего редактирования. Удалённая из файла табличка будет обнаружена заново, если шлюз возвращает её MAC со статусом `online`.

Все изменения `devices.json` через сервис выполняются под общей блокировкой с атомарной заменой. Запускайте один экземпляр сервиса с одним рабочим процессом (`--workers 1`), как в готовой службе systemd. Пользователю службы нужны права записи в каталог `app/` для создания временного файла и замены `devices.json`.

## Если список пуст или изменения не видны

| Ситуация | Что проверить |
|---|---|
| Нет связи со шлюзом | Питание шлюза, подключение Ethernet, доступность его IP и адрес API в `app/config.json`. Успешный `/health` подтверждает только работу нашего сервиса. |
| Табличка есть в окне **Таблички**, но отсутствует в выборе | Её локальный статус должен быть `base`, статус шлюза — `online`; IP таблички должен отвечать на ping с сервера. |
| Все таблички уже заполнены | Нажмите **⟳**, только если нужно вернуть все устройства для повторной отправки. |
| Новая табличка ещё не появилась | Включите её и запустите **Найти новые таблички**; записи `offline` не добавляются. |
| Вместо ожидаемого интерфейса открывается старая версия | Убедитесь, что открываете адрес машины с новой версией. Приложение на компьютере и приложение на шлюзе — разные экземпляры. |
| Не видны изменения HTML, JavaScript или CSS | Обновите страницу через **Ctrl+F5**. После изменения Python-кода или ручной правки `config.json` также перезапустите сервис. |
| Превью сообщает об отсутствии шрифта | Выберите доступный шрифт; на Linux проверьте установку DejaVu, при использовании `TC_FONT_PATH` — путь к файлу. |

## Рабочие данные и Git

В текущей структуре `app/config.json` и `app/devices.json` отслеживаются Git и не исключены через `.gitignore`. При работе сервис меняет их: сохраняет адрес шлюза, обнаруженные MAC, названия и статусы. Перед обновлением установки сохраняйте эти файлы; перед коммитом проверяйте их отдельно от исходного кода.

Для чистой установки используйте подходящий адрес API и пустой список устройств из примеров выше. Не заменяйте ими рабочие файлы действующей установки. Окружения `venv/`, `.venv/`, каталоги редакторов, Python-кэши, логи и временные файлы исключены через `.gitignore`.

## Проверки

Тесты используют временный `devices.json` и имитируют ответы шлюза; рабочие настройки и таблички не изменяются.

```powershell
.\venv\Scripts\python.exe -B -m unittest discover -s tests -v
```

В Linux используйте `./venv/bin/python -B -m unittest discover -s tests -v`.
